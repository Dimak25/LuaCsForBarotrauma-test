# План повышения производительности Barotrauma (для ИИ-агента и разработчиков)

Документ описывает поэтапную работу по ускорению игры **без поломки существующих функций** и сборку
оптимизированной версии. Он написан так, чтобы ИИ-агент мог выполнять этапы по одному, а человек — проверять результат.

- Основа: статический анализ кода (коммит `85ded59`). Номера строк ориентировочные — перед правкой ищите код по имени метода.
- Профилировщиком ничего не измерялось. **Все утверждения об узких местах — гипотезы, пока их не подтвердил замер (этап 1).**
- Код игры проприетарный (см. `EULA.txt`). Изменения предназначены для личной/тестовой сборки, если иное не согласовано с правообладателем.

## 0. Кратко: в чём проблема

Игра выполняет симуляцию **в одном потоке с фиксированным шагом 60 Гц** (`Timing.cs`, цикл накопителя в
`BarotraumaClient/ClientSource/GameMain.cs`, физика — `GameScreen.Update` → `GameMain.World.Step`).
Если тик длиннее ~16,7 мс, игра замедляется (накопитель ограничен `Timing.AccumulatorMax = 0.25`).
Производительность определяется скоростью **одного ядра** и давлением на GC, а не количеством ядер.

К поздней стадии растут: число предметов, трупов, ботов, проводов/сигналов, тел физики. Часть алгоритмов
линейна или квадратична по этим числам. Плюс слой LuaCs/Harmony добавляет накладные расходы на горячие методы.

## 1. Правила совместимости (нарушать нельзя)

Сборка играет с модами, поэтому «не сломать» означает не только «проходят тесты».

1. **Публичный и «публицизированный» API неизменен.** Проект использует `AssemblyPublicizer` (`Luatrauma.props`): C#-моды
   компилируются против **всех** членов игровых сборок, включая приватные, а Lua/Harmony-патчи находят методы по
   имени класса, имени метода и типам параметров. Поэтому нельзя:
   - переименовывать или менять сигнатуры существующих методов, полей, свойств, событий (включая приватные);
   - превращать поле в свойство и наоборот (например, `Item.IsActive` — публичное поле);
   - менять тип публичных коллекций (`Item.ItemList` и т. п.).
   Новые члены добавлять можно.
2. **Патчи `HarmonyEventPatchesService` привязаны к конкретным методам** (`Character.DamageLimb`, `Affliction.Update`,
   `Connection.SendSignal`, `Item.Use`, `Inventory.PutItem` и т. д.). Не менять их сигнатуры. Если оптимизация должна
   обойти патч, сохранить наблюдаемое поведение событий.
3. **Семантика хуков LuaCs сохраняется:** порядок подписчиков, побеждает последнее не-nil значение в `Call<T>`,
   исключения подписчика логируются и не прерывают остальных, подписка/отписка во время вызова допустима.
4. **Порядок обновления сущностей сохраняется** (порядок `Item.ItemList`, порядок компонентов). Логика опирается на него неявно.
5. **Сетевой протокол и формат сохранений не меняются.** Тесты сериализации (`INetSerializableStructTests` и др.) должны проходить.
6. **Мультиплеерная детерминированность:**
   - ГСЧ с `RandSync.ServerAndClient` и `RandSync.ClientOnly` не трогать и не вызывать из других потоков
     (`Rand.CheckRandThreadSafety` бросает исключение);
   - `Rand.Int`/`Rand.Range` без параметра `sync` — `Unsynced`, их поток можно менять безопасно.
7. **Многопоточность только там, где нет общего состояния.** Не параллелить `Item.Update`, `Character.Update`, `World.Step`,
   `Powered.UpdatePower`. Закомментированный `RUN_PHYSICS_IN_SEPARATE_THREAD` — не готовая опция.
8. **Поведение по умолчанию не меняется**, если изменение не является чистой оптимизацией. Всё, что меняет геймплей
   (частота обновлений, лимиты), — только за флагом и выключено по умолчанию.
9. **Один этап — один PR** (или один коммит), каждый с замерами и откатом.

## 2. Окружение и ограничения

- Нужен **.NET 8 SDK**. Сборка: `dotnet build LinuxSolution.sln -c Release /p:Platform=x64` (или `WindowsSolution.sln`, `MacSolution.sln`).
- Тесты: `dotnet test LinuxSolution.sln` (CI: `.github/workflows/run-tests.yml`, перед запуском создаётся каталог
  `~/.local/share/Daedalic Entertainment GmbH/Barotrauma`). Тестовый проект: `Barotrauma/BarotraumaTest`
  (`LinuxTest.csproj`, xUnit + FluentAssertions + FsCheck). Есть тесты LuaCs (`BarotraumaTest/LuaCs/HookPatchTests.cs`) и клиент-сервера (`ClientServer/`).
- Релизная сборка: `Deploy/DeployAll.sh` (запуск `dotnet run` в `Deploy/DeployAll`), результат в `Barotrauma/Deploy/bin/content`.
- **Папка `Barotrauma/BarotraumaShared/Content` в репозиторий не входит** (арт, XML предметов, звуки). Её копируют из легальной копии игры.
  Без неё нельзя загрузить раунд, поэтому бенчмарки на реальных сохранениях и часть тестов недоступны.
- **Если среда агента не имеет `dotnet` или `Content` (как облачная среда, где писался этот документ), агент обязан явно написать,
  что не собирал и не запускал**, и не выдавать непроверенное за проверенное.

## 3. Этапы

Каждый этап имеет: цель, действия, критерий готовности. Переходить к следующему можно только после выполнения критерия.

### Этап 1. Базовая линия (без изменения кода игры)

**Цель:** зафиксировать «до», чтобы любое ускорение было измеримо.

Действия:
1. Собрать Release-сборку клиента и сервера, прогнать `dotnet test`. Сохранить результат как «эталон» (список упавших тестов, если есть — не считать регрессией).
2. Подготовить набор сценариев (сохранения/сабы поздней стадии): много предметов, 10+ ботов, трупы, разветвлённая проводка, пожары/затопление, несколько подлодок/обломков. Записать, какие моды активны.
3. Снять метрики в игре командой консоли `showperf`. Счётчики: `Update:MapEntity:Items`, `Update:MapEntity:Misc`, `Update:Power`,
   `Update:Character`, `Update:StatusEffects`, `Update:Ragdolls`, `Update:Physics`, `Update:Particles`, `Update:GameSession`, `Draw:Map:Lighting` и др.
   Записать среднее и максимум времени тика/кадра.
4. Отдельно снять метрику **с LuaCs и без модов** и **с модами**, чтобы отделить вклад слоя LuaCs.
5. Добавить (в отдельном коммите, не в игровой логике) измерение аллокаций за тик через `GC.GetAllocatedBytesForCurrentThread()`
   и число сборок GC (`GC.CollectionCount(0/1/2)`).

Готово, когда: есть таблица «сценарий × метрика» для эталонной сборки, и определено, какие из гипотез H1–H12 подтверждены.
**Приоритет дальнейших этапов пересматривается по этим данным.**

### Этап 2. Страховочная сеть: тесты и золотой прогон

**Цель:** появиться способ заметить поломку до релиза.

Действия:
1. Для каждого метода, который будет оптимизироваться, написать **тест на характеристику текущего поведения**
   (в `Barotrauma/BarotraumaTest`), пока код ещё не менялся:
   - `EventService`: порядок подписчиков, возвращаемое значение `Call<T>`, подписка/отписка во время вызова, исключение в подписчике, алиасы Lua-событий (`think` → `IEventUpdate`);
   - подсчёт трупов по подлодкам и порог `CorpsesPerSubDespawnThreshold`;
   - перемешивание шлюзов: каждый шлюз обработан ровно один раз за тик, исходный список не ломается при удалении шлюза в `Update`;
   - `Item.Remove`: очистка `linkedTo` у других предметов;
   - `AddNearbyTargets`: тот же набор целей и порядок;
   - `PathFinder.FindPath`: тот же путь на фиксированном наборе узлов.
2. Написать **золотой прогон**: детерминированная загрузка сохранения, N тиков с фиксированным сидом, хеш состояния
   (позиции и условия предметов, положения/здоровье персонажей, вода в отсеках, заряд батарей, содержимое инвентарей).
   Для правок без изменения логики хеш **обязан совпасть побитно**. Для правок, меняющих `Unsynced`-ГСЧ (H2), сравнивать статистически, не побитно.
3. Убедиться, что новые тесты проходят на нетронутом коде.

Готово, когда: тесты характеристики зелёные на эталоне, золотой прогон воспроизводим (два запуска дают одинаковый хеш).

### Этап 3. Слой LuaCs / Harmony (H1, H12) — наибольший ожидаемый эффект, наименьший риск

**Цель:** убрать аллокации и блокировки на горячих путях, когда подписчиков нет.

Действия:
1. `EventService.PublishEvent` и `Call<T>`: сначала неблокирующая проверка «есть ли подписчики» (по снимку/счётчику), и только потом
   блокировка и создание замыканий. В вызывающих патчах не создавать замыкание/строку, пока не проверено наличие подписчиков
   (например, метод `HasSubscribers<T>()` в `IEventService`, добавленный **без изменения существующих сигнатур**).
2. Заменить связку `AsyncReaderWriterLock` + `.GetAwaiter().GetResult()` на синхронный `ReaderWriterLockSlim`
   или на неизменяемый снимок подписчиков (copy-on-write при подписке). Порядок подписчиков сохранить.
3. `TypeStringKey`: кэшировать нижний регистр (не вызывать `ToLowerInvariant()` на каждый поиск), кэшировать строки `"signalReceived." + identifier` по прототипу предмета.
4. Убрать `_subscribedEventDispatchers.ToImmutableArray()` из горячего пути (снимок обновлять при добавлении/удалении диспетчеров).
5. `Connection_SendSignal_Post`: не итерировать провода и не звать `Call`, если нет подписчиков ни на `IEventSignalReceived`, ни на `signalReceived.*`.
6. `LuaPatcherService`: если техника позволяет без изменения семантики — переиспользовать словарь параметров/`ParameterTable` (пулы), не создавать при отсутствии активных Lua-патчей. Этот пункт изолировать в отдельный PR: он самый рискованный в этом этапе.

Критерии: тесты `HookPatchTests` и новые тесты `EventService` зелёные; аллокации за тик в сценарии с проводкой снижены (цель — заметное снижение,
конкретное число зафиксировать по этапу 1); поведение хуков идентично.

### Этап 4. Мелкие безопасные правки (H2, H3, H4, H8, H11)

Каждый пункт — отдельный коммит с замером.

1. **H2:** `MapEntity.UpdateAll` — заменить `Gap.GapList.OrderBy(g => Rand.Int(int.MaxValue))` на перемешивание Фишера–Йейтса
   переиспользуемого буфера (копия списка сохраняет защиту от изменения списка во время итерации). ГСЧ остаётся `Unsynced`.
2. **H3:** `Character.UpdateDespawn` — считать трупы по подлодкам один раз за проход `Character.UpdateAll` (словарь) или
   поддерживать счётчик при смерти/удалении. Проверить, что порог `CorpsesPerSubDespawnThreshold` работает как раньше.
3. **H4:** `Powered.UpdatePower` — кэшировать список `Powered`-компонентов у предмета. Учесть инвалидацию при добавлении/удалении компонентов.
4. **H8:** `StatusEffect.ShouldWaitForInterval` — чистить таймеры удалённых сущностей реже или при удалении сущности, а не на каждый вызов. Проверить отсутствие утечек.
5. **H11:** `Settings.EnableDiagnostics` (Farseer) — выключить в Release, предварительно проверив поиском, что игровая логика не читает диагностические поля.

Критерии: золотой прогон совпадает (для H2 — статистически); тесты характеристики зелёные; замер показывает снижение времени и аллокаций.

### Этап 5. Структуры данных (H5, H6, H7) — средний риск

Каждый пункт: реализация за флагом или с `Debug.Assert`, сравнивающим со старым алгоритмом, на переходный период.

1. **H5 `Item.Remove`:** заменить полный обход `ItemList` для `linkedTo` обратным индексом. Сначала проверить, всегда ли связи
   двусторонние. Если нет — индекс должен учитывать односторонние. Пока индекс не доказан, оставить старый проход под `Debug.Assert`.
2. **H6 активные предметы:** добавить вспомогательную структуру активных предметов, **не меняя** публичное поле `IsActive`
   (моды пишут в него напрямую) и **сохраняя порядок обновления**. Быстрая проверка `!IsActive` уже есть — эффект стоит сначала измерить.
3. **H7 `NearbyItems`:** пространственная сетка/кэш вместо прохода по `Item.ItemList`. Сохранить порядок добавления целей и точное условие расстояния (`CheckDistance`), включая случай `TargetIdentifiers` для `powered`.

Критерии: золотой прогон совпадает побитно; тесты характеристики зелёные; проверка на сохранении с массовым удалением предметов (взрыв, очистка трупов) без фризов.

### Этап 6. ИИ ботов (H9) — средний/высокий риск (меняет решения ботов)

1. `AIObjectiveCleanupItems.IsValidTarget`: вычислять «в отсеке есть враг» один раз на обновление цели (по отсекам), а не на каждый предмет. Результат идентичен.
2. `PathFinder.FindPath`: заменить вставку в отсортированный список выбором ближайших кандидатов; **тай-брейк должен остаться тем же**, чтобы выбор стартового/конечного узла не менялся.
3. Проверка: записанные сценарии — пути ботов и выбор целей совпадают с эталоном.

Если совпадения добиться нельзя — оставить оптимизацию за флагом (по умолчанию выключено) и описать отличия.

### Этап 7. Рендер и свет (H10) — только клиент

1. `LightManager.AddRayCastTask`: заменить `pendingRayCasts.Any(...)` под блокировкой на `HashSet<LightSource>` (проверка O(1)). Порядок очереди сохранить.
2. Дальнейшие изменения отрисовки — только с визуальным сравнением скриншотов до/после и только при подтверждённом узком месте (`Draw:*` в `showperf`).

### Этап 8. Экспериментальное и опциональное (по умолчанию выключено)

- **Интервалы обновления** `MapEntity.MapEntityUpdateInterval`, `MapEntity.PoweredUpdateInterval`, `Character.CharacterUpdateInterval` (по умолчанию 1).
  Их увеличение меняет частоту логики (`deltaTime` умножается на интервал) и может влиять на баланс и моды. Только как опция настроек/консольной команды, не по умолчанию.
- **Настройки среды выполнения .NET** (`csproj`: `ConcurrentGarbageCollection`, `TieredCompilation`, `TieredPGO`, `TieredCompilationQuickJitForLoops`, размер gen0).
  Каждую менять отдельно и измерять на этапе 1; оставлять только с подтверждённым выигрышем без регрессии по паузам.
- **Значения по умолчанию, влияющие на геймплей** (`CorpsesPerSubDespawnThreshold`, `CorpseDespawnDelay`, `VisibleLightLimit`, `ParticleLimit`) — не менять без решения владельца проекта.

### Этап 9. Полная проверка и сборка

1. `dotnet build` всех конфигураций (Client/Server × Windows/Linux/Mac, если доступны) — без новых предупреждений об ошибках.
2. `dotnet test LinuxSolution.sln` — не хуже эталона этапа 1.
3. Золотой прогон — совпадение.
4. Матрица ручной проверки (пока нет автоматизации):
   - одиночная кампания: запуск, 3–5 локаций, сохранение/загрузка;
   - мультиплеер: хост + клиент, длинная сессия, отсутствие рассинхронов и ошибок в консоли;
   - моды: минимум один Lua-мод и один C#-мод (в т. ч. использующие `Hook.Add`, `Hook.Patch`, `signalReceived.*`, `think`);
   - подредактор/редактор уровней открывается и работает;
   - отсутствие новых сообщений об ошибках в консоли и в `Logs`.
5. Повторить измерения этапа 1 на итоговой сборке; заполнить таблицу «до/после».
6. Собрать релиз: `Deploy/DeployAll.sh` (или `.bat`). Артефакты — `Barotrauma/Deploy/bin/content`.
   Положить рядом отчёт: список изменений, замеры «до/после», известные ограничения.

```
Замеры до → после: время тика, аллокации/тик, GC-сборки
Не проверено: (честно перечислить)

```

## 5. Чего делать нельзя

- Менять сигнатуры существующих членов (в том числе приватных) без веской причины и без проверки моддинг-API.
- Параллелить основную симуляцию.
- Менять игровые значения по умолчанию «заодно» с оптимизацией.
- Объединять несколько этапов в один PR.
- Заявлять об ускорении без замера; заявлять о прохождении тестов, которые не запускались.
- Отключать тесты, чтобы «позеленело».

## 6. Критерий готовности всей работы

Собрана сборка, в которой: тесты не хуже эталона; золотой прогон совпадает (кроме описанных `Unsynced` отличий); ручная матрица пройдена;
задокументировано снижение времени тика и аллокаций на сценариях поздней стадии; все опциональные изменения выключены по умолчанию.
