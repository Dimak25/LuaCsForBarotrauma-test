## 3. Микробенчмарки (этап 1)

Только сборка Release: в Debug числа бессмысленны (бенчмарк это сам пишет в отчёте).
Строки «real code» измеряют настоящие `EventService` и `PerformanceCounter`. Строки «pattern» воспроизводят точное выражение из игры на
объектах-заглушках (для игровых объектов нужен `Content`), но с настоящим `Rand`. Строки «proposal» показывают, чего можно ждать от замены; это
не реализованные изменения.

### H1: слой событий LuaCs (настоящий код)

Три прогона; байты детерминированы, время шумит.

| Сценарий | нс/вызов | байт/вызов |
|---|---:|---:|
| эталон: прямой вызов интерфейса, без сервиса | 3–6 | 0 |
| `PublishEvent`, **0 подписчиков**, замыкание как в патчах | 240–415 | **264** |
| `PublishEvent`, 1 подписчик | 424–486 | 344 |
| `PublishEvent`, 10 подписчиков | 568–707 | 359 |
| `Call("signalReceived." + id, …)`, 0 подписчиков (паттерн патча `Connection.SendSignal`) | 267–333 | **344** |

Вывод: вызов события без единого подписчика стоит в 50–100 раз дороже прямого вызова и выделяет 264 байта. Патч `Connection.SendSignal`
делает `PublishEvent` **и** `Call` на каждый провод каждого сигнала (~600 байт и ~0,5–0,75 мкс). Этот слой работает
даже в игре без единого Lua-мода.

Иллюстративная арифметика (число вызовов **предположено, а не измерено в игре**): при 2 000 доставок сигнала за тик выходит ~1–1,5 мс
на тик и ~1,2 МБ аллокаций на тик, то есть около 70 МБ/с при 60 Гц, что даёт частые сборки GC поколения 0.
Реальные частоты нужно снять в игре (раздел 5).

### H13: встроенный профайлер (новая гипотеза)

`PerformanceCounter.AddElapsedTicks`: 116–138 нс и **40 байт** на вызов (боксинг перечислителя очереди в `Average`). Вызывается ~15–20 раз за тик,
то есть ≈ 2,5 мкс и ≈ 800 байт на тик: **пренебрежимо мало**. В приоритет не берём.

### Что это меняет в приоритетах

1. **H1 (слой событий LuaCs)** — единственная гипотеза, подтверждённая измерением как накладные расходы, растущие с числом сигналов и
   афликций, а не с чем-то редким. Остаётся приоритетом №1 (этап 3 плана).
2. **H2, H3, H13** — микровыигрыши (десятки мкс на тик). Делать после H1, ради постоянной нагрузки на GC, а не ради миллисекунд.
3. **H5–H9** (обход всех предметов, `NearbyItems`, ИИ, `Item.Remove`) — по-прежнему главные кандидаты на реальные миллисекунды на поздней стадии,
   но **это гипотезы**: доказательство даст только замер в игре.

## 4. Метрика аллокаций в игре (этап 1, п. 5)

Коммит `1a15288`. В оверлей `showperf` добавлена строка
`Alloc (main thread): N KB/s  GC/s gen0/1/2: a/b/c`. `PerformanceCounter.SampleGcStats` вызывается раз в секунду рядом с расчётом частоты
обновления. Только диагностика, игровая логика не менялась. Код компилируется, но **отображение в игре не проверялось** (нет `Content`). Считаются
аллокации только главного потока (поток света и загрузки не учитываются).

## 6. Этап 2: страховочная сеть

### Сделано

- `Barotrauma/BarotraumaTest/Performance/EventServiceCharacterizationTests.cs` — **35 тестов** на поведение `EventService`: публикация, подписка/отписка, диспетчеры,
  алиасы Lua-событий (`think`), «старые» строковые события (`Add`/`Call`/`Remove`), жизненный цикл (`Reset`, `Dispose`). Зависимости подменены через
  `DispatchProxy` (`TestDoubles.cs`), поэтому папка `Content` не нужна.
- Тесты, имя которых начинается с `Quirk_`, фиксируют поведение, похожее на случайное. Оно закреплено, чтобы его изменение было осознанным
  (изменили специально → обновите тест в том же коммите и напишите об этом в PR):
  1. Диспетчеры (`AddDispatcherEventService`) **не получают событие**, если у основного сервиса нет подписчиков на этот тип события: `PublishEvent`
     выходит раньше, чем пересылает диспетчерам.
  2. `Unsubscribe(string eventName, string identifier)` **не находит** подписчиков, зарегистрированных по типу (`Subscribe<T>`): ключи не равны, и вызов
     молча ничего не делает.
  3. Результат Lua-функции, вернувшей несколько значений (`return "a", true`), конвертируется **целиком как кортеж**, а не по первому значению. Для `Call` (тип
     `object`) вызывающий получает `DynValue[]`. Для типизированного `Call<string>`/`Call<double>` MoonSharp бросает `ScriptRuntimeException`
     («cannot convert a tuple to a clr type»): в Release её ловит `catch` внутри `EventService`, пишет ошибку в лог и возвращает `default`, в Debug исключение
     пробрасывается наружу. Код читается так, будто побеждает первое значение, но это не так.

### Исправления к плану по итогам разведки

- **Порядок подписчиков не определён.** Подписчики лежат в `ConcurrentDictionary`, порядок обхода зависит от хеша. Поэтому «сохранять порядок подписчиков»
  из плана надо читать как «не полагаться на порядок и не вводить новую зависимость от него». Тесты порядок намеренно не проверяют.
- **Старые тесты LuaCs отключены.** `BarotraumaTest/LuaCs/HookPatchTests.cs` и `LuaCsFixture.cs` целиком закомментированы (`/* ... */`, «TODO: Rewrite all of this»).
  Утверждение плана «тесты `HookPatchTests` зелёные» неверно: их нет. Патчи Lua (`LuaPatcherService`) сейчас тестами не покрыты.

### Не сделано, и почему

| Что | Причина |
|---|---|
| Тесты характеристики для `Gap`-шаффла, подсчёта трупов, `Item.Remove`, `AddNearbyTargets`, `PathFinder` | Нужны настоящие `Item`, `Gap`, `Character`, `Submarine`: их конструкторы требуют префабы из `Content`. Выделить чистую логику без правки игрового кода нельзя |
| Золотой прогон (детерминированный прогон N тиков с хешем состояния) | Требует загрузки сохранения, то есть `Content`. Не реализован; проектировать его нужно на машине с `Content` |

## 7. Уроки и открытые вопросы

- CI (`on-push-*.yml`) запускает `dotnet test LinuxSolution.sln` без `-c`, то есть в **Debug**, а в Debug `EventService` ведёт себя иначе (`#if DEBUG throw;`
  при исключении подписчика и при дубликате алиаса). Первый вариант теста про кортеж прошёл в Release и упал в Debug: **проверяйте тесты в обеих конфигурациях**.
  Сейчас оба прогона зелёные (раздел 2).
- Запуск GitHub Actions на ветке `claude/tender-dirac-f8rpg9` при написании отчёта не обнаружен (`list_workflow_runs` вернул 0 запусков), то есть подтверждения из настоящего CI нет,
  только локальные прогоны.
- Одновременный запуск нескольких `dotnet build`/`dotnet test` в одной среде приводит к зависанию (в Debug-прогоне 11 минут при ~1 % CPU). Запускайте
  сборки последовательно, лучше с `-nodeReuse:false`.
- Метрика аллокаций в `showperf` не проверена визуально (нужен запуск игры с `Content`).
